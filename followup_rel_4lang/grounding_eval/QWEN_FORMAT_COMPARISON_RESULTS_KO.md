# Qwen 위치 지정: JSON과 `(x, y)` 직접 비교

실행일: 2026-11-04. 이 문서는 [v3 재검토](QWEN_V3_REASSESSMENT_KO.md)의 **출력 형식 가설**을 실제 Qwen2.5-VL-7B-Instruct 추론으로 점검한 탐색 결과다. 기존 [v3 프로토콜](PROTOCOL_KO.md)의 게이트를 통과하거나 본 분석을 시작한 결과가 아니다.

각 응답의 전문과 `addCriterion` 사례는 [원시 출력 뷰어](QWEN_RAW_OUTPUT_VIEWER.html)와 [읽는 법·오류 점검](QWEN_RAW_OUTPUT_AUDIT_KO.md)에 모았다. 여기서의 ‘대조군’은 **F 조건이 아니라**, 질문과 GUI 언어가 같은 8개 위치 지정 기능 검사다.

## 비교 설정

- 고정 체크포인트 `cc594898137f460bfe9f0759e9844b3ce807cfb5`, BF16·SDPA, 픽셀 예산 262,144–2,097,152, greedy·최대 64 새 토큰, 이미지 1장, 명시적 system 메시지 없음. Qwen chat template의 기본 system은 그대로다. 48개 파일럿 이미지의 해시와 실제 전처리 격자를 추론 전에 재검사했다.
- 이미 본 **같은 언어 양성 대조 8화면**에서 `전체 관계 질문/짧은 기준 표현 × JSON/(x, y)` 네 조건을 **같은 모델 적재 세션**에서 실행했다(새 응답 32개). 전체 질문과 짧은 표현의 프롬프트 문구는 기존 [파일럿 보고서](QWEN_PILOT_RESULTS_KO.md)의 두 템플릿을 그대로 썼다. 각 템플릿 **안에서** 마지막 출력 지시만 다음처럼 바꿨다.

```text
JSON: Return only this JSON array: [{"point_2d": [x, y]}]. No explanation or code fence.
괄호: Return only one coordinate as (x, y). No explanation or code fence.
```

- 잠금 파일럿 12문항 × 4 GUI 언어 × O/R = **96개 입력**에는 짧은 표현과 괄호 출력을 새로 실행했다. 같은 96개의 JSON 출력은 [기존 원시 결과](../results/grounding_pilot_qwen_phrase_v1/pilot.jsonl)를 재사용했다. [분석 코드](analyze_qwen_format_comparison.py)는 문항 ID·입력 이미지 해시·전처리 격자·모델 revision·렌더링된 프롬프트가 대응하며 마지막 출력 지시만 다름을 96개 전부 검증한다.
- 주 판정은 원본 이미지로 역변환한 점이 주석 bbox 안에 있는지다. JSON은 점 하나의 기존 파서, 괄호는 **출력 전체가 `(정수, 정수)`인 경우에만** 허용하는 새 파서를 썼다. 범위 밖 좌표·불완전 출력·추가 설명은 실패로 처리했다. 유효 출력률과 위치 적중률을 따로 집계했다.
- 기존 JSON 대조군 8개씩을 다시 생성했을 때 **전체 질문 8/8, 짧은 표현 8/8의 원시 출력이 이전 기록과 글자 단위로 동일**했다. 이는 이 러너의 이전 파일럿 대비 재현성 확인이다. 이전 REL full의 `from_pretrained` 어댑터와 생성 결과가 동등하다는 검사는 아니다.

## 양성 대조 8화면: 형식과 대상 지정

| 기준 요소 입력 | 출력 | 유효 점 | GT bbox 적중 |
| --- | --- | ---: | ---: |
| 전체 관계 질문 | JSON | 6/8 | 0/8 |
| 전체 관계 질문 | `(x, y)` | 6/8 | 1/8 |
| 짧은 기준 표현 | JSON | 3/8 | 3/8 |
| 짧은 기준 표현 | `(x, y)` | 6/8 | 6/8 |

같은 전체 질문에서 JSON→괄호로 바꾼 결과 유효 점은 **6/8 그대로**였고, 적중은 **0→1/8**이었다. 즉 괄호 출력을 요구해도 전체 관계 질문에서 기준 요소 대신 다른 요소를 찍는 문제가 대부분 남았다. 짧은 표현에서는 유효 점과 적중이 각각 **3→6/8**로 늘었지만, 여전히 사전 지정한 양성 대조 **8/8 유효** 게이트에 미달했다.

전체 질문과 짧은 표현은 텍스트 길이뿐 아니라 도입 지시문도 다르다. 이 표로 두 입력 방식의 차이를 **기준 표현 길이만의 인과효과**라고 해석하지 않는다. 형식 비교는 각 입력 방식 내부에서만 통제돼 있다.

## 짧은 표현 O/R 파일럿 96응답: 같은 입력의 짝 비교

| 출력 | 유효 점 | GT bbox 적중 | O 적중 | R 적중 |
| --- | ---: | ---: | ---: | ---: |
| 기존 JSON | 43/96 | 43/96 | 20/48 | 23/48 |
| 새 `(x, y)` | 52/96 | 47/96 | 22/48 | 25/48 |

괄호 출력의 유효율은 **+9/96 = +9.38%p**, 전체 위치 적중률은 **+4/96 = +4.17%p**다. 그러나 같은 96개 입력을 짝지으면 위치 정오는 `0→1` **14개**, `1→0` **10개**, `1→1` **33개**, `0→0` **39개**다. 유효 출력도 새로 얻은 19개와 잃은 10개가 상쇄됐다. 12문항을 복원추출 단위로 한 탐색적 10,000회 bootstrap(고정 seed 20261104)의 **위치 적중 차이 95% 구간은 −13.54~+20.83%p**다. 이 작은 파일럿은 괄호 출력의 일관된 우위를 뒷받침하지 않는다.

GUI 언어별 적중 건수(각 24응답)는 EN **12→12**, ZH **12→11**, TH **8→10**, RU **11→14**였다. 언어별 표본은 24개이고 같은 12문항을 공유하므로, 개별 언어 개선 주장으로 사용하지 않는다.

괄호 출력은 96개 중 **44개가 무효**였다. 그중 **35개에 `addCriterion`이 포함**됐고, 무효 출력 7개가 64토큰 상한에 닿았다. 원문에서 숫자 두 개가 들어간 괄호 패턴이 검색되는 무효 출력은 2개지만, 하나는 완성된 좌표 뒤에 두 번째 미완성 좌표가 이어졌고 다른 하나는 설명문에 되풀이된 원점 `(0, 0)`이다. 둘을 유효한 단일 점으로 사후 구제할 수 없다. 기존 JSON 파일럿의 무효 출력 53개 중 `addCriterion` 41개와 비교하면 반복 출력 문제가 괄호 형식에서도 계속된다. 괄호 형식의 유효 점 52개 중 5개는 GT 밖이었다. 출력 형식의 변화가 파싱뿐 아니라 예측한 위치에도 영향을 준 셈이다.

## 판정과 제한

**JSON만 제거해서는 v3 문제를 해결하지 못했다.** 전체 관계 질문에서는 정상 좌표를 내더라도 기준 요소를 놓치는 문제가 남았다. 짧은 표현과 괄호를 함께 쓰면 대조군은 나아졌지만, 96개 O/R의 형식 유효율 **52/96**은 사전 지정 게이트 **90/96**에 크게 못 미친다. 따라서 이 결과로 괄호 형식을 본 분석의 새 프로토콜로 확정하거나 158문항 추론을 시작하지 않는다.

이 비교는 이미 살펴본 8개 대조와 12문항 파일럿에서 이루어졌다. 새 프로토콜 선택에는 이들과 본 분석 158문항에서 분리된 양성 대조군이 필요하다. `addCriterion`의 원인과 이전 full 어댑터 대비 적재 경로 동등성도 아직 확정되지 않았다.

원시 출력·렌더링 프롬프트·이미지 해시·점수는 [이번 대조군](../results/grounding_format_comparison_v1/controls.jsonl), [괄호형 O/R](../results/grounding_format_comparison_v1/pilot_phrase_tuple.jsonl), [검증·집계 결과](../results/grounding_format_comparison_v1/analysis.json)에 있다. 재실행 코드는 [비교 러너](run_qwen_format_comparison.py)이며, 저장된 결과의 CPU 재분석은 다음 한 줄로 수행한다.

```bash
.venv/bin/python followup_rel_4lang/grounding_eval/analyze_qwen_format_comparison.py
```
