# Qwen 위치 지정 v3 재검토: JSON, 대상 지정, 일반화 가능한 규칙

검토일: 2026-11-04. **문헌·저장된 출력 재분석이며 새 추론은 하지 않았다.** 기존 [v3 프로토콜](PROTOCOL_KO.md), [파일럿 결과](QWEN_PILOT_RESULTS_KO.md), [이전 MPR-GUI 설정 대조](BASELINE_ALIGNMENT_AUDIT_KO.md)를 소급 변경하지 않는다. 아래는 다음 버전의 검증안이지, 통과한 새 프로토콜이 아니다.

이후 실제 JSON↔`(x, y)` 파일럿 비교는 [별도 실행 결과](QWEN_FORMAT_COMPARISON_RESULTS_KO.md)에 기록했다.

## 결론부터: JSON이 문제일 수 있는가?

**출력 안정성에는 관여할 수 있지만, 현재 실패를 JSON 하나로 설명할 수 없다.** Qwen2.5-VL [기술 보고서](https://arxiv.org/abs/2502.13923)는 점·상자에 이미지 크기 기반 절대 좌표를 사용하고 JSON, XML, 자체 형식의 학습 데이터를 설명한다. [Qwen 팀의 예시](https://qwenlm.github.io/blog/qwen2.5-vl/)에는 `point_2d` JSON 배열이 실제로 있다. [HyperClick 논문 부록 A.2](https://openreview.net/pdf?id=LsWreF9ff4)도 Qwen2.5-VL의 GUI 위치 평가에 `point_2d` JSON 배열과 `label`을 요청한다. 따라서 JSON 자체가 Qwen에 부적합하다는 문헌 근거는 없다. 그렇다고 이 형식이 이 모델·과제의 유일한 표준이거나, 우리 파일럿에서 안정적이라는 뜻도 아니다.

저장된 Qwen 출력은 서로 다른 두 실패를 보여 준다.

| 입력 | 형식상 유효한 점 | GT bbox 적중 | 해석 |
| --- | ---: | ---: | --- |
| v3 전체 관계 질문, 양성 대조 8개 | 6/8 | 0/8 | JSON을 제대로 낸 6개도 **관계 질문의 답 쪽**을 가리켰다. 나머지 2개는 12·18토큰 뒤 닫히지 않은 출력이므로 64토큰 상한에 걸린 사례는 아니다. |
| 짧은 기준 표현, 양성 대조 8개 | 3/8 | 3/8 | 맞게 파싱된 점 3개는 전부 기준 요소 안에 있었다. |
| 짧은 기준 표현, 탐색 O/R 96개 | 43/96 | 43/96 | 유효한 43점은 전부 적중했다. **형식 게이트는 실패**했으며 O/R 언어 효과의 증거가 아니다. |

짧은 표현 O/R의 무효 출력 53개 중 41개는 `addCriterion` 반복, 8개는 점이 없는 `[]`, 2개는 잘린 JSON, 1개는 코드 블록, 1개는 닫는 문자 오류다. 53개 중 숫자 두 개가 완성된 `[x, y]` 흔적은 2개뿐이다. 따라서 파서를 느슨하게 하거나 코드 블록만 허용해도 대다수는 복구되지 않는다. `[]`는 문법적으로 JSON이지만 **점이 없다**. 반복 토큰의 원인은 출력 형식, 프롬프트, 생성 종료, 파일럿 전용 가중치 적재 방식 중 어느 것인지 분리되지 않았다. v2→v3 및 v3→짧은 표현의 차이는 입력과 메시지 구성이 함께 달라진 비교이므로 특정 변경의 효과로 읽지 않는다.

## 문헌에서 직접 가져올 수 있는 범위

| 1차 자료 | 실제 확인한 규칙 | 이 연구에 적용할 때의 한계 |
| --- | --- | --- |
| [Qwen2.5-VL 기술 보고서](https://arxiv.org/abs/2502.13923), [Qwen 예시](https://qwenlm.github.io/blog/qwen2.5-vl/) | Qwen2.5의 점·상자는 **입력 이미지 크기 기반 절대 좌표**다. `point_2d` JSON도 지원되는 표현이다. | 어떤 영어 지시문, `<ref>` 태그, system 메시지가 최적인지는 입증하지 않는다. 보고서 자체가 여러 출력 형식의 학습을 설명한다. |

**통일된 단일 프롬프트나 `JSON 금지`라는 일반 규칙은 찾지 못했다.** 여러 연구에서 공유하는 수준은 *대상 요소를 분명히 지정하고, 모델이 해석할 수 있는 좌표를 한 번 내게 하며, GT bbox와 비교하고, 입력·출력 계약을 기록하는 것*이다. 특정 모델 평가기의 긴 system, guided prefix, 좌표 표기법을 조합해 새로운 “표준”을 만들지 않는다.

## 이 연구에 맞는 실험 규칙

1. **목표 변수를 먼저 고정한다.** 진단하고 싶은 것은 관계 질문의 정답 요소가 아니라 `<ref>`로 표시된 **기준 요소**의 위치다. 전체 질문을 유지한다면 ‘질문에 대한 답’과 ‘기준 요소’를 구별할 수 있는지 별도 기능 검사한다. v3의 유효 출력 6개가 모두 틀린 것은 이 검사 실패다.
2. **좌표계는 실제 모델 입력 이미지로 고정한다.** 현재 Qwen 러너처럼 `image_grid_thw`에서 최종 크기를 얻어 절대 픽셀을 요청하고, GT 채점 전에 원본 크기로 역변환한다. 화면 해상도·픽셀 예산·그리드를 기록한다.
3. **출력 형식은 단순하게, 두 형식만 직접 비교한다.** v3의 `[{"point_2d": [x, y]}]`는 근거 있는 기준안이다. 비JSON 대안은 진짜 `(x, y)`로 둔다. `[x, y]`도 JSON이므로 JSON 여부의 비교안이 아니다. 괄호 형식이 더 좋다는 선행 증거는 없으며, 오직 형식 부담 가설을 검사하는 대조안이다.
4. **한 번에 하나의 축만 바꾼다.** 동일한 이미지·텍스트·기본 system·greedy 생성·토큰 상한에서 JSON↔괄호만 바꿔 출력 형식 효과를 본다. 그 다음, 각 형식 안에서 전체 관계 질문↔기준 요소를 설명하는 짧은 표현을 비교한다. 짧은 표현은 문항의 원래 말을 보존하고 O/R 간에는 잠금 기준 span만 바꾼다. v2처럼 새 system을 동시에 추가하지 않는다.
5. **형식 실패와 위치 실패를 나눠 보고한다.** 완성된 한 점 추출률, 요청 형식 준수율, 전체 입력 대비 point-in-box 적중률을 각각 제시한다. 주 지표에서 미출력·불완전 출력은 실패로 센다. 유효 출력에 한정한 위치 정확도는 보조 지표이며 O/R 효과의 주 지표로 바꾸지 않는다. 원시 텍스트와 종료 토큰 수를 남기고, 사후에 임의의 숫자를 찾아 점으로 인정하지 않는다.
6. **선택과 평가를 분리한다.** 이미 확인한 12문항 파일럿의 O/R 차이나 158문항 본 분석을 보고 프롬프트를 고르지 않는다. 새로운 양성 대조군에서 기능성과 형식만 확인하고, O/R 언어 효과를 보기 전에 프로토콜을 잠근다. 모든 언어·조건에 같은 선정 프롬프트와 채점기를 쓴다.
7. **이전 객관식 실행과의 연결을 정확히 쓴다.** 초기 6×6과 REL full의 system은 조건별로 바뀌지 않았으나 A–D 전용 지시였다. 위치 과제에는 그 문구를 그대로 넣을 수 없다. 다음 위치 시험도 v3처럼 명시적 system을 추가하지 않는 정책을 유지하고 렌더링된 기본 system까지 기록한다. 동일 체크포인트·전처리·모델 적재 방식도 대조한다.

## v3를 기준으로 한 최소 검증안

**0단계: 실행 경로 점검.** 원래 REL full 어댑터의 `from_pretrained` 적재와 파일럿 전용 가중치 순차 적재가 같은 입력에서 같은 점 출력을 내는지 소수 샘플로 확인한다. 다르면 프롬프트 비교 전에 적재·토크나이저·생성 경로를 바로잡는다. 이 검사는 두 실행의 **동등성**을 확인하는 기능 시험이지 형식을 고르는 데이터가 아니다.

**1단계: 출력 형식만 바꾸는 쌍 비교.** 같은 새 양성 대조 화면에 v3 문장과 이미지·`<ref>`·전체 관계 질문을 그대로 사용한다. 마지막 출력 지시만 A/B로 바꾼다.

```text
A (기존): Return only this JSON array: [{"point_2d": [x, y]}]. No explanation or code fence.
B (대안): Return only one coordinate as (x, y). No explanation or code fence.
```

`B`도 v3의 “integer pixel coordinates”, 화면 폭·높이, 원점 설명을 그대로 둔다. 파서는 두 형식을 각각 엄격하게 정의한다. 출력 형식을 바꾸면서 느슨한 파서·예시 숫자·생성 옵션까지 같이 바꾸지 않는다. 64토큰 미만에서 끝난 v3의 불완전 출력은 토큰 상한 증가만으로 해결된다고 가정하지 않는다.

**2단계: 대상 지정 검사.** 1단계에서 JSON 또는 괄호 출력이 안정되더라도, 전체 질문 조건에서 기준 요소 적중이 낮으면 짧은 기준 표현으로 *별도* 입력 비교를 한다. 이를 위해 v3의 이미지, 좌표, 출력 문장, 기본 system을 유지하고 `Question: {marked_stem}`을 `Reference phrase: {descriptor}`로 바꾸며 첫 문장의 `question below`만 `reference phrase below`로 맞춘다. 가능하면 **같은 대조 화면에 두 입력 × 두 출력 형식의 네 조합**을 적용한다. 출력 형식의 차이는 *각 입력 방식 안에서* 비교하고, 입력 방식의 차이도 *각 출력 형식 안에서* 비교한다. 짧은 표현은 현재 12문항에만 있으므로 158문항으로 가려면 전 문항의 O/R 표현을 작성·검수해야 한다.

**표본과 판단.** 이미 본 8개 대조·12문항 파일럿은 오류 진단에만 쓴다. 프롬프트 선택에는 본 분석 158문항과 겹치지 않는 **새 양성 대조 화면**을 GUI 언어 EN/ZH/TH/RU, 앱, 목표 상자 크기에 걸쳐 준비한다. 예를 들어 언어당 6개씩 24개를 같은 후보 조합에 짝지어 적용하고, 위치 타깃 GT를 먼저 검수한다. 실행 전에 형식 추출·GT 적중의 최소 기준, 언어별 실패 허용 범위, 동률 처리 규칙을 수치로 고정한다. 형식만 개선되고 기준 요소 적중이 회복되지 않으면 v3는 여전히 부적합하다.

이 검증안은 프로토콜 선택을 위한 기능 시험이다. 어느 후보가 통과해도 그 결과만으로 원래 객관식 REL 추론의 내부 grounding을 직접 관측했다는 주장은 하지 않는다.
