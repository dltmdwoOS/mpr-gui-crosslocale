# REL grounding 후속 실험: 설계 검토안

상태: **검토안, 아직 동결 전** (2026-10-26). 이 문서는 기존 결과와 데이터 구조를 재사용해 다음 실험의 판정 범위를 정한다. 모델 추론이나 새 annotation은 수행하지 않았다. 구조적 179문항 전체와 그 안의 12문항 파일럿은 [`annotation/rel_grounding`](../annotation/rel_grounding/README_KO.md)에 outcome-blind manifest와 네 화면 동시 bbox 검수 UI로 준비했다. 실제 사람 검수 두 건이 다음 필수 단계다.

## 1. 연구 질문과 현재 근거

질문은 (1) GUI 언어로 바꾼 질문의 기준 요소 표현이 해당 요소의 위치 파악을 개선하는가, (2) 그 변화가 REL 객관식 정답 변화와 어떻게 연결되는가, (3) 기준 요소 표현과 선택지 표현의 기여는 각각 얼마인가이다. 현재 O/R/C/F 결과는 답의 변화를 보여주지만 모델 내부에서 어느 단계가 실패했는지는 직접 보여주지 않는다.

기존 R은 질문 속 기준 요소 표현 **뿐 아니라 A–D 선택지의 GUI 연결 표현도** 바꾼다. 원본 문제가 없는 text-dependent 불일치 3,576개 언어쌍 중 2,674개에서 질문과 선택지가 모두 바뀌었다. 따라서 기준 요소 bbox 하나에 대한 O/R 점찍기만으로 기존 R−O 전체를 설명하면 안 된다.

구조적으로는 한 개의 질문 기준 span, 원본 문제 없는 12개 방향성 언어쌍을 가진 220문항(2,640쌍, GUI 이미지 최대 880개)이 있다. 그중 질문과 선택지가 **12쌍 모두 실제로 달라지는** 문항은 179개(2,148쌍, 이미지 최대 716개)다. 이는 자동으로 얻은 *후보*이며, 단일한 화면 요소를 가리키는지와 번역이 동등한지는 아직 사람 검증이 필요하다. 예를 들어 `rel::3/backend_1.jpg`의 `Calculator`는 앱 인터페이스 전체를 가리킬 수 있고, `rel::2/map_9.png`의 `Avoid Tolls`와 태국어 대응은 의미 검수가 필요하다.

## 2. 판정 가능한 주장

| 관측/조작 | 지지할 수 있는 주장 | 단독으로는 말할 수 없는 것 |
|---|---|---|
| O/R의 명시적 위치 지정 정확도 차이 | 표현 변화가 *별도의 명시적 grounding 과제* 수행을 바꾸는가 | 객관식 답변 중 실제 내부 grounding 과정의 변화 |
| 아래 2×2 객관식 조건 | 질문 기준 표현과 선택지 표현 **문자열 묶음**의 정답률 기여 | OCR·번역·시각 탐색·관계 추론의 개별 인과 기여 |
| 위치 지정 전환과 객관식 정답 전환의 동반 | 두 과제 결과의 연관 | 엄밀한 매개효과 또는 개별 오류의 원인 |
| GT 기준 요소 위치를 알려주는 보조 개입 | 기준 요소 위치 정보가 오류를 구제할 수 있는가 | 구제되지 않은 오류가 곧 관계 추론 오류라는 결론 |

명시적 위치 지정은 [ScreenSpot/SeeClick](https://arxiv.org/html/2401.10935v2)에서 쓰는 GUI grounding 진단과 형식이 맞는다. 이 문항은 클릭 가능한 요소만 있는 데이터가 아니므로, 아래의 대상 요소 정의와 크기별 평가가 특히 중요하다.

## 3. 권장 핵심 설계

### 3.1 모집단과 검수

1. **구조적 주 분석 후보:** 위 179문항의 원본 문제 없는 12개 불일치 언어쌍. 기존 예측의 정오나 flip 여부로 문항을 고르지 않는다. 220문항의 나머지 41개는 문자열 변경이 없는 언어쌍을 포함하므로 별도 보조 표로 남긴다. 이 선택은 전체 적격 text-dependent 301문항 중 179문항에 한정되므로 전체 REL로 무조건 일반화하지 않는다.
2. **사람 판정:** 각 후보에서 질문의 유일한 span이 하나의 화면 요소를 지시하는지, 4개 GUI 로캘에서 그 요소를 찾을 수 있는지 확인한다. `ambiguous`, `multiple_matches`, `absent`, `unpointable`, `screenshot_error`를 기록한다. 화면의 한 행·섹션·앱 전체처럼 경계가 모호한 경우 규칙 없이 큰 bbox를 그리지 않는다. 번역 의미의 두 필드는 기본 `yes`이며, 눈에 띄는 문제만 `no/uncertain`으로 표시한다. 이 절차는 번역 동등성을 전수 검증하지 않는다.
3. **주 분석 포함:** 기준 요소 bbox가 판정 가능하고 명시적으로 발견된 번역 문제가 없는 언어쌍을 사용한다. `yes`는 번역 검증 완료를 뜻하지 않으므로, 남을 수 있는 번역 오류를 해석의 한계로 보고한다. 제외 사유별 수와 언어별 비율을 모두 공개한다. 사람 판정자는 모델 답과 O/R flip을 보지 않는다.
4. **GT 단위:** `parallel_id × GUI 언어 × 실제 이미지`의 기준 요소 bbox를 원본 이미지 픽셀 좌표로 한 번 기록하고, 같은 화면을 쓰는 source 언어쌍에 재사용한다. `ref_id`, 요소 역할(button/label/control/section 등), 원본 폭·높이, 이미지 SHA-256, bbox, 검수 상태를 저장한다. label과 control이 분리되어 있으면 둘 다 기록하고 질문이 지시하는 UI 요소를 primary box로 고정한다.

### 3.2 기준 요소와 선택지의 2×2 객관식 비교

질문의 **문맥과 GUI 이미지·정답·선택지 순서**를 고정하고 두 문자열 묶음을 독립적으로 바꾼다.

| 조건 | 질문 기준 요소 span | A–D의 GUI 연결 span | 상태 |
|---|---|---|---|
| O | source | source | 기존 예측 재사용 |
| R_stem | GUI | source | 새 추론 |
| R_opts | source | GUI | 새 추론 |
| R | GUI | GUI | 기존 예측 재사용 |

기존 `reference_mappings.jsonl`과 O/R 행에서 `R_stem`/`R_opts`를 재구성하고 사람이 의미를 검수한다. 질문 속 기준 요소가 하나인 문항만 주 분석에 쓴다. 선택지 측은 여러 span의 **묶음 조작**이므로 개별 선택지 효과라고 부르지 않는다. 새 조건도 기존과 같은 두 모델 revision, GUI 이미지, 전처리, greedy, 객관식 프롬프트를 쓴다.

주 대비는 기준 표현의 평균 효과 `[(R_stem−O)+(R−R_opts)]/2`, 선택지 표현의 평균 효과 `[(R_opts−O)+(R−R_stem)]/2`, 상호작용 `R−R_stem−R_opts+O`다. O→R_stem은 선택지를 source로 고정하므로 기준 요소 grounding 결과와 연결해 볼 가장 깨끗한 객관식 대비다. 기존 O→R은 전체 효과로 별도 보고한다.

### 3.3 독립 grounding 과제

같은 화면에 대해 source 표현과 GUI 표현을 각각 제시하고 **질문에 등장한 기준 요소 하나의 위치**를 묻는다. 질문의 다른 관계 정보와 A–D 선택지는 주 grounding 프롬프트에 넣지 않는다. 문맥이 필요한 경우 원문의 기준 요소 명사구(예: `the 'Avoid Tolls' toggle switch`)를 쓰되, O/R 두 프롬프트는 매핑된 span만 달라야 한다. 그 명사구와 지시 대상은 사람 검수 후 고정한다. 영어 위치 지정 지시문, 모델별 출력 형식, 이미지와 생성 설정은 O/R 내에서 같다.

- Qwen2.5-VL: 절대 pixel point 또는 box 출력 형식을 파일럿에서 검증한다. [공식 설명](https://qwenlm.github.io/blog/qwen2.5-vl/)은 이미지 크기에 기반한 절대 좌표를 사용한다고 한다. 현재 러너의 이미지 resize 결과를 기록해 **모델 입력 좌표에서 원본 이미지 좌표로의 변환**을 확인한다.
- InternVL2.5: 모델의 [공식 grounding 데이터 형식](https://internvl.readthedocs.io/en/latest/get_started/chat_data_format.html)은 `[0,1000]` 정규화 bbox다. 실제 고정 8B 모델의 출력은 파일럿으로 확인하고, box 중심을 원본 이미지 좌표로 변환한다.
- 두 모델의 좌표를 같은 원본 이미지 공간으로 옮겨 `point-in-GT-box`를 **주 지표**로 계산한다. 파싱 실패·범위 밖 좌표는 주 지표에서 오답이다. 유효 출력률, 정규화 중심 거리, 대상 bbox 면적별 정확도는 보조 지표다. 서로 다른 좌표 형식 때문에 두 모델의 원시 위치 정확도 자체를 단순 비교하지 않는다.

### 3.4 위치 정보 개입과 해석 범위

위치 지정과 객관식의 동반 변화는 매개효과의 증거가 아니다. 주 진단 뒤, 같은 기준 요소의 **GT 위치를 O와 R 객관식 입력에 똑같은 형식으로 제공**하는 작은 보조 실험을 미리 계획한다. 위치 단서가 O를 더 많이 구제하고 R−O 격차를 줄이면 기준 요소 위치 파악이 병목이라는 해석이 강해진다. 단서 자체의 주의 집중 효과를 보기 위해 길이와 형식이 맞는 중립 단서를 둔다. 올바른 선택지의 위치나 정답 레이블은 제공하지 않는다. 단서가 구제하지 못해도 선택지 grounding, OCR, 번역 및 관계 추론 중 어디가 실패했는지는 판별되지 않으므로 필요하면 후보 선택지 전체의 위치를 별도 annotation하는 2단계 진단으로 간다.

## 4. 파일럿과 동결 게이트

1. 구조적 179문항에서 REL 하위 유형별 2개씩 **12문항**을 모델 결과를 보지 않고 뽑아 파일럿으로만 쓴다. 4개 GUI 화면씩 최대 48개를 이중 annotation하고, source→GUI 방향은 GUI 언어가 각각 포함되도록 제한해 출력 형식과 참조 대상 판정 가능성을 확인한다. 파일럿 문항은 주 분석에서 제외한다.
2. 파일럿에서는 쉬운 단일 UI 요소의 positive control도 넣어 좌표 파싱과 변환이 되는지 검증한다. 프롬프트 선택은 **출력 유효성과 좌표계 정확성**으로만 하고, O/R 정답 차이를 보고 최적화하지 않는다. 양쪽 검수자가 같은 요소를 지시하는지와 box 차이, `unpointable` 비율을 확인한다. 주 실험 전에 positive control 좌표 파싱률과 대상 요소 합의율의 최소 허용치를 문서화한다. 미달 시 과제/annotation 규칙을 수정하고 새 파일럿으로 확인한다.
3. 동결 문서에 최종 대상 요소 정의, 제외 규칙, 프롬프트 전문, 모델 revision·전처리·출력 토큰 수, 좌표 변환, 주/보조 지표, primary sample과 pair weighting, 다중 비교/신뢰구간 방법, 파일럿 제외 ID, 입력 해시를 적는다. 이때 주 실험의 새 `R_stem`/`R_opts` 및 grounding 예측은 아직 보지 않는다.
4. 주 분석은 같은 `(parallel_id, source, GUI, model)` 내 조건을 짝지어 비교한다. **문항을 resampling 단위**로 하는 cluster bootstrap 95% 구간을 우선하고 언어쌍별 결과는 탐색적으로 보고한다. 12개 쌍의 일부가 의미 검수에서 빠지면 각 문항 내 유효 쌍을 동일 가중한 문항 평균을 사용하고, 전체/제외 수를 보여준다. 두 모델의 결과를 독립적인 문항 표본으로 합치지 않는다.
5. 기존 O/R 결과로 만든 가설임을 밝힌다. 이 실험은 동일 문항에 대한 **새로운 진단/개입**이지 독립 데이터셋 재현은 아니다. 주 결과를 `grounding 0→1`과 `REL 0→1`의 사례 표 하나로 요약하거나, 개별 오류를 `grounding failure`/`reasoning failure`로 확정 분류하지 않는다.

## 5. 현재 할 일

1. 준비된 네 화면 동시 UI로 12문항 블라인드 파일럿의 판정 가능성과 bbox 합의를 확인한다. 번역 동등성의 기본값 `yes`는 검증 결과로 해석하지 않는다.
2. 필요하면 판정 규칙을 수정한 뒤 전체 179문항을 독립 검수한다. 파일럿 12문항은 주 분석에서 제외한다.
3. 파일럿 합의율과 전체 검수의 유효 대상 수를 보고 보조 위치 단서 실험의 규모를 확정한 뒤 프로토콜을 동결한다.
4. `R_stem`/`R_opts` 객관식과 O/R grounding 러너를 구현하고, 고정 프로토콜대로 실행한다. 기존 객관식 러너는 최대 2토큰·A–D 파서이므로 위치 출력에는 별도 prompt/parser 계약이 필요하다.

현재 저장소에는 O/R/C/F full 결과와 GLMM, grounding 전체 annotation 도구가 있고, 사람 bbox annotation·grounding 예측은 없다. 장시간 GPU 추론은 이 검토 단계에서 시작하지 않는다.
