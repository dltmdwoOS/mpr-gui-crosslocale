# GUI 언어 불일치에 대한 REL 방법 개발 최종 보고서

**최종 방법은 PP-OCRv5 기반 질문 참조 정렬·보기 전체 번역이다.** Qwen3-VL-8B가 먼저 질문 본문의 GUI 이름을 추출한다. 다음 호출은 화면 문자열 목록을 참고해 그 이름의 교체 표현을 고르고, 네 보기를 GUI 언어로 번역한다. 코드는 본문의 참조 부분만 바꾸고, 같은 Qwen3-VL-8B가 수정 문제와 원본 화면으로 답한다. 전체 개발 158문항·1,895쌍에서 **1,483개 정답(78.26%), 계산시간 78.98분(2.501초/쌍)**으로 전체 평가를 끝낸 자동 방법 중 정확도가 가장 높았다.

같은 모델과 PP-OCRv5로 **질문 참조만 정렬**한 방법보다 50개 더 맞혔다(+2.64%p, 95% CI [+0.16, +5.07])고, 계산시간은 10.68분 늘었다. 태국어 GUI에서 67개를 더 맞혔고 나머지 GUI 언어를 합하면 17개를 덜 맞혔다. 4B에도 같은 방법을 적용한 결과는 73.98%였다. 따라서 4090 재실험에서는 8B를 사용하고, 전체 평균과 GUI 언어별 결과를 함께 기록한다. 현재 수치는 B200 MIG에서 얻은 개발 결과다. ## 실험 범위와 이름 읽는 법

출발점은 질문 본문과 보기의 참조를 화면 언어에 맞추면 다국어 GUI의 text-dependent REL 성능이 회복된다는 이전 병렬 입력 실험이다. 이번 개발은 **병렬 번역이나 정답 참조 경계를 모르는 상태에서 화면과 원본 객관식 문제만으로 그 효과를 얼마나 재현할 수 있는지** 물었다. 기존 benchmark, grounding, 병렬 정렬은 비교의 배경이다. 아래 기록은 자동 현지화 개발이 시작된 데이터 검증부터 최종 방법을 선택한 시점까지 다룬다.

## 10. 4090 검증에 가져갈 방법과 고정 설정

**이름은 ‘PP-OCRv5 기반 질문 참조 정렬·보기 전체 번역’으로 고정한다.** 방법을 처음 제시할 때는 ‘풀이 모델의 분리 편집’이라고 덧붙인다. 구현에서 유지할 경계는 다음과 같다.

| 단계 | 입력과 동작 | 출력과 검증 |
| --- | --- | --- |
| 화면 읽기 | 스크린샷과 알려진 GUI 언어로 PP-OCRv5를 실행 | 중복을 제거해 정렬한 문자열 목록. 좌표·읽기 순서·신뢰도는 편집 입력에서 제외 |
| 질문 참조 추출 | 이미지 없는 Qwen3-VL-8B에 원본 본문과 원문 언어만 제공 | 실제 GUI 이름의 최소 원문 범위. 문자열과 출현 위치를 확인해 코드에서 범위 ID 생성 |
| 질문 이름 선택·보기 번역 | 같은 모델이 원본 문제, 참조 범위, 두 언어, 화면 목록을 입력받음 | 참조마다 화면 목록의 정확한 문자열 또는 null. A–D는 전체 문자열로 번역하며 화면에 없는 설명·오답 보기도 의미를 보존하도록 지시 |
| 검증과 조립 | 질문과 보기 묶음을 따로 확인 | 질문은 검증된 범위만 치환. 보기 네 개의 키·순서와 새 중복을 확인. 구조 실패는 해당 부분만 한 번 복구하고 남은 실패 부분은 원문 유지 |
| 최종 풀이 | 수정한 문제, 원본 스크린샷, 새 대화로 같은 Qwen3-VL-8B 호출 | 생성한 A–D 답으로 채점. 숫자·관계·부정 변화 경고는 편집 품질 진단에 기록 |

PP-OCRv5는 RapidOCR 3.10.0과 Paddle Inference 3.3.0 CUDA13, mobile 검출기 및 영어·중국어·태국어·동슬라브 인식기를 사용했다. 검출 최대 변 960, 인식 batch 8, 추가 인식 신뢰도 컷은 0이다. 평가 Qwen3-VL-8B-Instruct revision은 `0c351dd01ed87e9c1b53cbc748cba10e6187ff3b`, 4B는 `ebb281ec70b05090aa6165b016eac8ec08e71b17`, 비교에 사용한 고정 Qwen3-8B는 `47719a242beab8f9aecc40ce3928b034dd5dd559`다. [OCR 가중치 잠금](../configs/ppocrv5_paddle_models.json) · [기존 OCR 방법의 상세 설정](PPOCR_STEM_ALIGNMENT_WRAPUP_KO.md)

최종 방법은 BF16·SDPA·greedy·seed 42, 입력 상한 4,096 토큰을 사용한다. 편집 batch는 1이며 참조 추출 출력 상한은 768, 질문 이름 선택과 보기 전체 번역은 1,024 토큰이다. 같은 단계의 복구에도 같은 상한을 적용한다. 최종 풀이는 최대 2MP, batch 3, 최대 신규 2 토큰, `channels_last_3d` 패치 설정이다. 첫 구조 탐색은 768 토큰 변환과 별도 구조 복구 없는 설정, 복원 이후 전사·분리 편집은 전사 768→3,072, 추출 768, 정렬 512 토큰과 구조 복구 설정을 썼다. 별도 문제 전체 번역에는 의미 경고에 대응하는 복구 경로가 있었고, 직접 완성 문제 재작성은 768 토큰에서 구조를 검사했다. 외부 연구의 영어 이해 후 단계별 풀이는 두 모델 호출 모두 최대 512 토큰이었다. 각 실행의 실제 메시지·모델 설정·코드와 입력 체크섬은 해당 프로토콜과 결과 자료에 남아 있다. [초기 프롬프트](PROMPTS_AND_GO_NO_GO_KO.md) · [복원 프롬프트](TWO_STAGE_V2_PROTOCOL_KO.md) · [최종 참조 추출 지시](../stem_refinement_2x2.py) · [최종 편집·검증 코드](../editor_matrix.py) · [실행 설정](PPOCR_EDITOR_MATRIX_RUNBOOK_KO.md)

4090 파일럿은 화면 면적이 큰 Screen 4문항의 48쌍에서 원본 풀이, 질문 참조만 정렬, 최종 방법을 비교한다. 실행 코드는 CPU 모의 흐름을 통과했다. 4090의 실제 peak 메모리·시간·예측 일치도는 파일럿에서 기록한다. 이후 전체 재실험에는 같은 분모와 설정을 사용하고 장비별 기존 예측 캐시를 분리한다. 기존 PP-OCR 목록을 재사용해 편집·풀이를 재현하는 경우와 새 장비에서 OCR까지 재실행하는 경우는 시간 집계에서 구분한다. ### 결과 집계 밖의 개발 작업

- 데이터 검증, CPU 모의 실행, 스키마·복원 검사, 단건 GPU 점검, 배치 재사용 검증과 메모리 점검은 구현 검증으로 기록했다. 이 출력은 성능 표의 분모에서 제외했다. [검증 하네스](STEP1_REPORT_KO.md) · [초기 메모리 검토](PIPELINE_OOM_AUDIT_KO.md) · [최종 편집 기능 점검](PPOCR_EDITOR_MATRIX_RUNBOOK_KO.md)
- 참조를 보호하고 나머지 문맥을 영어 또는 모델 선호 언어로 옮기는 확장은 코드와 CPU 검사까지 진행했다. 그 정확도·오류율·비용은 미측정이다. 유사도 검색이나 새 NER·bbox·grounding을 포함한 후속 방법도 이번 완료 성능 표에서 별도로 평가된 조건이 없다. [문맥 언어 전환 준비 기록](STEP4_REPORT_KO.md)
- 전체 문제 번역은 앞선 초기·복원 실험에 포함돼 있다. PP-OCRv5로 화면 목록을 고정한 마지막 비교는 질문 참조 정렬과 보기 전체 번역의 조합을 평가했다. 동일 프로토콜의 전체 문제 번역, 보기만 번역하는 조건, 366문항 확장, 다른 모델·문항 유형의 일반화 결과는 후속 검증 범위다. [마지막 비교 설계](PPOCR_STAGE2_MATRIX_DESIGN_KO.md)
